# Registry 五到十人观察测试

这轮测试只回答一个问题。第一次打开 Registry 的人，能不能在没有主持人提示的情况下找到一个可信的 Skill，并完成下一步动作。

当前页面没有完整的产品漏斗。数据库里存在浏览表，前端没有调用。站点也没有把搜索、详情查看、复制安装串起来。测试入口因此使用独立的本地记录器，避免把社区功能中的匿名设备 ID 当成研究数据。

## 测试入口

本地或预览站点后面加上 `?study=1&cohort=2026q3`。页面会出现一块橙色研究面板。

`cohort` 只接受 `2026q3` 这种季度批次。不要把姓名、邮箱或参与者编号放进 URL。参与者编号只保存在主持人的离线记录表里。

参与者同意以后再点 `Start study`。记录只留在当前标签页的 `sessionStorage`，不会上传。它不保存搜索词、来源网址、浏览器信息和个人标识。参与者结束后点击 `Finish & copy`，随后把 JSON 交给主持人。复制失败时可以点 `Download JSON`。

现有点赞和评论会访问 Supabase。主持人若要做完全离线的观察，应当要求参与者不要使用这两项社区功能，并在本地预览环境运行测试。

## 参与者怎么选

第一轮先找五人。至少三人最近三个月用过 Claude Code、Codex 或同类编程助手，但从未用过这个 Registry。另找一名经常安装 Skill 的熟练用户，再找一名维护过开源工具的人。

如果五人出现了两种截然不同的行为，再补三到五人。补测对象应当来自分歧最大的那一类，不要为了凑到十人平均分配。

同一团队、已经看过项目演示、参与过仓库开发的人不进入首轮。他们知道页面想表达什么，会掩盖真正的新用户问题。

## 邀请文案

我在测试一个开源 Skill 搜索站，想看第一次使用的人会在哪里犹豫。全程约二十五分钟，需要共享屏幕并边操作边说出想法。我们不测试你的技术水平，也不会记录搜索词和个人信息。你愿意帮我做一次吗。

## 主持人开场

今天测试的是页面。哪里看不懂，责任都在页面。请像平时一样操作，看到什么就说什么。遇到困难可以继续尝试，也可以停下来。我不会教你按钮在哪里。

得到口头同意以后，主持人请参与者打开研究链接并点 `Start study`。不要提前解释 Featured、Leaderboard、Stars、Official 或社区评分的含义。

## 三个任务

### 任务一 找到候选项

请找一个能帮你检查代码安全问题的 Skill。你可以使用页面上的任何入口。找到后告诉我，你为什么点开它。

主持人只观察。参与者问该搜什么时，回答“按你平时的理解来”。连续三分钟没有进展就结束这个任务，并记录卡住的位置。

### 任务二 做出信任判断

请看刚才打开的 Skill。假设你今天就要在真实项目里使用它，决定你会安装、继续调查，还是放弃。请把让你做出决定的页面信息说出来。

完成选择以后追问两句。你还缺什么信息。哪一条现有信息最有用。不要主动提安全扫描、维护时间、作者、来源或代码内容。

### 任务三 完成下一步

如果你愿意安装，请复制安装命令。如果你想继续调查，请打开你最想看的外部页面。如果你决定放弃，请返回并找另一个候选项。

任务结束后请参与者点击 `Finish & copy`，把 JSON 保存到本次观察记录里。

## 主持人记录表

| 字段 | 记录内容 |
|---|---|
| 参与者编号 | 只用 P01 到 P10 |
| 背景 | 新用户、熟练用户或维护者 |
| 首次动作 | 搜索、快捷标签、榜单、随机或其他 |
| 首次打开详情用时 | 从页面加载到打开第一个 Skill |
| 最终决定 | 安装、继续调查或放弃 |
| 决定依据 | 尽量记参与者原话 |
| 缺失信息 | 参与者主动提出的内容 |
| 明显卡点 | 位置、动作和持续时间 |
| 导出文件 | 对应的 JSON 文件名 |

屏幕录像需要参与者另行明确同意。没有同意就只做现场笔记和事件导出。

## 事件怎样读

| 事件 | 含义 |
|---|---|
| `search_submitted` | 参与者输入查询、按回车或点快捷标签，只保留搜索长度区间和结果数量区间 |
| `skill_detail_opened` | 打开一个 Skill 详情 |
| `favorite_toggled` | 收藏或取消收藏 |
| `install_copy_clicked` | 点击复制安装命令，表示安装意图，不能证明命令已经运行 |
| `github_opened` | 从详情页进入 GitHub 继续调查 |
| `full_search_requested` | 从精简索引切换到完整搜索 |

单次导出用于还原操作顺序。五到十人的样本太小，不适合拿转化率小数点做结论。优先看重复发生的卡点、参与者自己说出的判断依据，以及他们在详情页之后选择复制、调查还是离开。

## 什么时候改页面

五人中有三人在同一处失败，可以直接进入修复。两人遇到同一问题，先看它是否阻断主任务。阻断寻找、信任判断或下一步动作的问题也应修复。只有一人提出、且不影响任务的偏好先记入候选清单。

第一轮最值得验证的信号有两个。一个是参与者能否在三分钟内打开合理候选项。另一个是详情页现有信息能否支持明确决定。多数人说不出为什么可信时，下一轮应先补证据信息，再继续加分类、榜单或社区功能。

## 每轮结束后的产物

每位参与者保留一份记录表和一份 JSON。整轮结束后写一页归纳，只列重复问题、反例和对应证据。页面改动与观察结论分开提交，第二轮使用同样任务复测，才能知道问题是否真的消失。
